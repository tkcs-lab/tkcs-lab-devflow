# Plan 93: one inherited repo-admin policy for every repository of an organisation

> Historical record once merged: read it only to understand why a change was made.

## Summary

**Use it:** An organisation's own small policy holds `org` and `extends: [<shared base pin>, <private org file pin>]`, each pin `<owner>/<repo>/<path>@<40-hex commit>`. `validate-policy` resolves it (`--resolved`, `--explain`, `--kind`, `--public`, `--offline`), `latest-pin` prints the pin to write, and `audit` reads each repository's small `.tld/admin-policy.yaml` and audits the effective policy per repository. The new `policy` check proposes, as pull requests, an override written from what the repository shows (required checks, release parameters) or converted from an old whole policy; `--no-detect` skips the detection.

**Scope:** The policy model, `extends` fetch through the API, the per-repository merge, derived logins, detection, and the docs, schema, starters, playbook, a stub eval and the spec for them. Policies without `extends` behave as before. The branch carries the head of PR 104 (plan 90's implementation); the feature pull request is retargeted onto PR 104's branch and merges only after PR 104. Departures from the ask: `repos` (the exceptions) is set only in the policy file that is run, not in a repository; item 8 is plan 90's p12 and p13, which this plan builds on instead of copying; there is no disk cache; an override that loosens a guarded setting is held back, not only reported.

**Security:** The extended files and the override files are read with the owner's token and merged into what the audit may change, so each is checked for credentials, shape, schema and key class; an override cannot set organisation-level keys, a loosening is clamped back and reported, and no inherited file can switch on a deletion or a revocation. `--yes`, `--allow-delete` and the dry run are unchanged.

**Performance:** Detection costs about 22 API calls per repository without a merged override, on every audit until the proposal is merged.

**Review focus:** The keep-live rules that stop inheritance from dropping a ruleset check or rewriting a tuned release workflow (3.7); the key classes, guarded and irreversible tables (3.3, 3.6); the API fetch and the reachability rule (3.4); detection (3.9); building on the unmerged PR 104 and the names taken from its code (3.12).

## 1. Goal

Make the repo-admin policy generic and inherited, as asked in [issue #93](https://github.com/tkcs-lab/tkcs-lab-devflow/issues/93), the way plan 90 does it for the profile. Today each repository keeps a whole copy of the organisation policy and the copies drift. After this plan the organisation keeps one shared base (in `tkcs-lab/.github`, public) and a private file of organisation-level sections (in `<org>/git-ops`), each organisation has one small policy that extends both, and each repository keeps only its own overrides. The owner's answers: the `.github` repositories are public, the shared base lives in `tkcs-lab/.github` at `tld/admin-policy-base.yaml` and both organisations extend it, and the organisation-level sections go into a separate private file.

## 3. Design

The architect role designed 3.1 to 3.11; each choice names what was rejected. Names are final.

### 3.1 Layers and where the merge happens

Order, later wins: the files of `extends` in the order listed, the run file (the policy file given to `--policy`), then the repository's override file. Mappings merge key by key; lists and scalars replace (the owner's rule, as in plan 90). The result of the first two layers is the **organisation policy** (`ctx.p`). The **effective policy** of a repository is `ctx.pol(repo)`.

**Chosen:** `Ctx.p` stays the organisation policy; a new `Ctx.pol(repo)` returns one repository's effective policy and every per-repository check reads it inside its `one(repo)`. Without `extends` in the run file (`Ctx.inherited` false) `pol(repo)` returns `ctx.p` and nothing extra is read, so old files and every existing test behave identically. **Rejected:** a sub-`Ctx` per repository (the `only`/`partial`/`repos` properties and the organisation-wide "unused" scans would need special cases, finding order would change, every check test would change). The 24 sites split: organisation-level and unchanged: `check_org`, `check_members`, `check_apps`, `check_tokens`, `check_protection`, `check_secrets`, `check_variables`, `check_labels`, `check_webhooks`, `check_keys`, `check_branches`, and `Ctx.repos`; moved to `pol(repo)` inside `one(repo)`: `check_repo`, `check_security`, `check_actions`, `check_rulesets`, `check_agent`, `check_release`, `check_files` (`config_dirs`, `workflows`, `release.environment`), `check_lint`. `workflow_source` keeps `ctx.p` for `_dir` (a `path` template comes only from the run file). Without `extends` the early `if not want: return []` guards and the single organisation-level reviewer lookup of `check_release` stay where they are (no new request); with `extends` the guards move inside `one(repo)`, because an override may write a section the organisation policy lacks, and the reviewer id is looked up per repository.

### 3.2 The four file kinds

| Kind | Where it comes from | `org` | Checked as |
|---|---|---|---|
| run | the file given to `--policy`, a private local checkout | required | `validate_policy(kind="run")` (the default) |
| base | any file named by `extends`, public or private | absent | `key_errors(kind="base")` |
| override | a repository's `.tld/admin-policy.yaml` | absent | `key_errors(kind="override")` |
| legacy | a repository file that has `org` (an old whole policy) | present | converted in memory to an override |

`validate_policy(policy, base_dir=None, kind="run", where="", public=None, inherited=False)` keeps its defaults so old callers are unchanged (`{}` still gives `missing required key 'org'`); `kind` override or base also returns the class errors of `key_errors`, `inherited=True` skips the rule that an `agent` or `release` section needs its login, and `public` names the repository when a base's repository is public. A repository file that has `org` is legacy and is converted, not rejected. The command line has `--kind auto|run|override|base` (default `auto`: run when `org` is present, else override). A kind other than run validates against a copy of the schema without the top-level `required`.

### 3.3 Key classes (tables in `repo_admin_policy.py`)

- `RUN_ONLY = ("org", "extends", "repos")`: only the run file. `repos` holds the exceptions (`exclude`), `override_path` (default `.tld/admin-policy.yaml`, a relative path without `..`) and `allow_loosen` (3.6). An override that could set `repos.exclude` would exempt its own repository, so it is refused there. An empty or missing `extends` means the policy is not inherited.
- `PRIVATE_ONLY = ("org_settings", "members", "apps", "tokens", "secrets", "variables")`: allowed in the run file and in an extended file of a private repository; refused in an extended file of a public or internal repository.
- `ORG_LEVEL = PRIVATE_ONLY + ("labels", "webhooks", "deploy_keys", "branches", "branch_protection", "profile", "git_ops")`: the run file or any extended file; never an override. (`profile` and `git_ops` are plan 90's p12 sections, the item 8 settings; they are organisation-specific and go into the organisation's private file.)
- `OVERRIDABLE = ("repo_settings", "security", "actions", "rulesets", "agent", "release", "workflow_lint", "config_dirs", "workflows", "workflow_params")`: the run file, a base (except the per-repository keys) and an override.
- `PER_REPO_ONLY = ("rulesets.default_branch.required_status_checks", "workflow_params", "config_dirs.known", "workflows[].params")`: allowed in an override and in the run file (the old single-repository use); refused in a base.
- A test asserts that these tables classify every top-level property of the schema (26 properties after p4, `profile` and `git_ops` among them), so a new key cannot slip through unclassified.
- `null` is refused anywhere in a base or an override, so an override cannot delete a section.

### 3.4 `extends`: grammar, fetch, no cache

- `extends` is a string or a list of one to four strings; an empty list (the starter's) means none and the policy is not inherited. Each entry is `<owner>/<repo>/<path>@<40-hex commit>`, the grammar and pin rule of plan 90 section 3.2 (a tag or branch is rejected; the tag stays as a trailing YAML comment). Two entries naming the same `<owner>/<repo>/<path>` are an error. **Rejected:** a string only (the owner's answer needs two files).
- **Fetch:** `GET /repos/{owner}/{repo}/contents/{path}?ref=<sha>` through the run's client, so a private file is readable with the owner's token and the audit needs no checkout; `GET /repos/{owner}/{repo}` gives `private`, `visibility` and `default_branch`; `GET /repos/{owner}/{repo}/compare/{default_branch}...{sha}` must answer `behind` or `identical` (the pin is an ancestor of the default branch), so a commit on an unreviewed branch of the base repository is refused. **Rejected:** plan 90's anonymous git fetch (cannot read the private file, needs a checkout).
- **No disk cache** (a departure from plan 90, which caches under the git directory): the audit is online by nature, a commit-addressed fetch costs three calls per file and a private file should not rest on a disk outside a repository. The run memoises each file once.
- **Reuse of plan 90 (`src/tld/profile/base.py` in PR 104):** `BaseRef` (owner and repo lower-cased, path, sha; properties `source` and `label` = `<source>@<sha7>`) and `parse_extends(value)` for the grammar. Today `parse_extends` raises `BaseError` with the fixed prefix `toolkit.yaml: 'tld.extends'` and the hint `run tld profile base latest <source>`, and `check_base_text(text, label)` runs, under the prefix `toolkit.yaml: base <label>: `, the size limit (`MAX_BYTES` 65536), UTF-8 without BOM, `_scan_events` (anchors and aliases, depth `MAX_DEPTH`, keys for which `secret_like_name` is true), `secret_scan.scan_text(decoded, skip_marked=False)` (an allow mark does not exempt a line), YAML and a mapping on top, then the profile's own `_key_errors` and the profile schema. p3 makes two compatible edits there: `parse_extends(value, label="toolkit.yaml: 'tld.extends'", hint="tld profile base latest {source}")`, and `check_base_shape(text, pre) -> (dict | None, errors)` split out of `check_base_text` (everything before `_key_errors`), which `check_base_text` then calls with its own prefix; the defaults keep every profile text, and `base.py` stays within its 600-line bound. It never copies the code. PR 104 accepts a pin that a version tag points at or that is an ancestor of the default branch head (`_require_approved`); the admin rule here accepts only an ancestor of the default branch, so a tag on an unmerged commit is refused.
- Every extended file and every override goes through `check_base_shape` and then through `validate_policy` of its kind (schema, unknown keys and class errors, once); the merged result is validated again as a run policy with `inherited=True`, so an unknown key or a wrong type anywhere is an error. An override comes from a repository an agent can edit, and anchors are an expansion vector.
- Errors (printed with the prefix `policy: `; `<i>` the index; `<label>` is `<owner>/<repo>/<path>@<sha7>`):
  - `'extends[<i>]': must be <owner>/<repo>/<path>@<40-hex commit SHA> (got '<value>')`
  - `'extends[<i>]': '@<ref>' is not a commit SHA; pin the base by its full 40-hex commit (a tag can move): run tld ops repo-admin latest-pin <owner>/<repo>/<path>` (plan 90's text with its command swapped through the `hint` keyword)
  - `'extends': <owner>/<repo>/<path> is listed twice`
  - `'extends[<i>]': cannot read <label> (HTTP <status>: <message>); a private file needs a token that can read it (GH_TOKEN, GITHUB_TOKEN or gh auth login)`
  - `'extends[<i>]': <sha7> is not on the default branch of <owner>/<repo>; pin a commit that was merged there`
  - `base <label>: sets 'extends'; an extended file cannot extend another`
  - the plan 90 token text with the label `base <label>:`: `base <label>: refused: line <n> looks like <kind> (pattern: <name>); the value is not shown. A base never holds a credential.`
- `tld ops repo-admin latest-pin <owner>/<repo>/<path>` prints `{"sha": "<40-hex>", "tag": "<tag>"}`: tags through the API, newest by numeric components (`^v?\d+(\.\d+)*$`, at most 20 tried), the first whose commit has the file; otherwise the default branch head with `"tag": null`; it exits 1 with `latest-pin: <path> does not exist in <owner>/<repo>` when no commit has the file.

### 3.5 Merge, workflows and the resolved view

- `deep_merge(base, over)`: mappings merge, lists and scalars of `over` replace. `merge_layers(layers)` returns the merged dict and a map from dotted leaf key to the layer label that set it.
- **Workflows.** The base lists the templates without parameters: `workflows: [{template: release}, {template: land}]`. A repository sets parameters without restating the list through the new override key `workflow_params: {release: {tag_prefix, version_style, check_script, create_release}}`; `apply_override` copies them into the entries of the effective `workflows` list by template. A repository whose release workflow is its own writes `workflows: [{template: land}]` (lists replace). An override's `workflows` entries may hold only `template`, `params` and `remove`; `path`, `dest` and `repos` are refused there and in a base because the file comes from a repository and `path` cannot be resolved remotely; a base entry may hold only `template`. **Rejected:** merging `workflows` by template (it is unclear whether a one-entry override drops `land`).
- **Resolved view.** `validate-policy POLICY --resolved` prints the merged policy as YAML (keys that start with `_` left out); `--explain` prints one line per leaf, `<dotted key> = <json>  # <source>`, sorted, with the sources `run`, `base <label>` and, for the leaves an override sets, `override <repo name>`; `--org-policy FILE` with an override file prints the effective policy of that repository over that organisation policy. The OK line stays `policy: OK (<path>)` for a run file and ends `, repository override` or `, base` for the other kinds.

### 3.6 Safety

1. **Irreversible switches.** `IRREVERSIBLE = (secrets.delete_unused, variables.delete_unused, labels.delete_unused, labels.delete_unlisted, webhooks.delete (non-empty), deploy_keys.delete_unused, branches.delete_merged, tokens.fine_grained.max_unused_days, tokens.fine_grained.revoke_expired)`. A base that sets one to a value that turns it on is refused: `base <label>: '<key>' turns on an irreversible change; set it only in the policy file you run`. `revoke_expired` defaults to true, so `clamp_irreversible(merged, run_doc)` sets `tokens.fine_grained.revoke_expired` to `false` when the run file has no `tokens.fine_grained` and a base supplied one. The sections of these keys are organisation-level, so an override cannot set them either. `apply_findings`, `--yes` and `--allow-delete` do not change.
2. **Guarded settings** (`GUARDED`): must stay true: `security.*` (five keys), `rulesets.tags`, `workflow_lint.require_permissions`, `workflow_lint.forbid_pull_request_target`; must stay false: `rulesets.default_branch.admin_bypass`, `actions.can_approve_pull_request_reviews`; ordered (stricter last): `actions.default_workflow_permissions` (write, read), `workflow_lint.pin_actions` (third_party, all), `agent.branch_policy` (protected_branches, default_branch); must equal the organisation's value: `repo_settings.allow_merge_commit`, `allow_squash_merge`, `allow_rebase_merge`; lists that may not shrink: `config_dirs.forbid`, `config_dirs.require`. `loosened(org, eff)` compares only keys the organisation policy sets. `clamp_guarded(org, eff, allowed)` puts the organisation's value back (a shrunk list gets its dropped entries back) and returns the `Loosening` records; the `policy` check warns `<repo>: the override sets <key> to <value>, looser than the organisation's <value>; the organisation value applies`. The run file may allow it: `repos.allow_loosen: {"<repo name glob>": ["<guarded key>", ...]}`. Dropping a template from `workflows` is information only, not guarded. The run file's own loosening of what its bases say is reported (`warn`, scope the organisation) and not clamped, because the run file is the owner's.
3. **Public base.** An extended file in a public or internal repository may not set a `PRIVATE_ONLY` section: `<where>: '<section>' is organisation-private and <repository> is public; keep org_settings, members, apps, tokens, secrets and variables in a file of a private repository` (`<repository>` is `<owner>/<repo>`, or `the repository this file goes into` for a local file checked with `--public`). `validate-policy --kind base --public` applies the same rule to a local file before it is committed.
4. **Class errors** (`<where>` is `<owner>/<repo>:<path>` for an override read from a repository, else the file path): `<where>: '<key>' is organisation-level; only the organisation's policy and the files it extends may set it`; `<where>: '<key>' is set only in the policy file you run` (for `org`, `extends` and `repos` in an override or a base); `base <label>: '<key>' is per repository; set it in each repository's override file`; `base <label>: 'workflows[<i>].params' is per repository; use workflow_params in each repository's override file`; `base <label>: 'workflows[<i>].<key>': a base may set only template`; `<where>: 'workflows[<i>]': a repository override may set only template, params and remove`; `<where>: '<key>': null is not allowed`; `'repos.override_path': must be a path below the repository root (no absolute path, no '..')`; `'repos.allow_loosen': '<key>' is not a guarded key`.
5. Pull-request deletions (`config_dirs.forbid`, `workflows[].remove`) are reviewed pull requests, not held by `--allow-delete`; a base may set `config_dirs.forbid` (it opens a reviewable deletion pull request in every repository) but never a workflow `remove`.
6. An override with problems is an `error` finding of the `policy` check; that repository is then audited with the organisation policy alone.

### 3.7 The per-repository audit

`Ctx` gains `inherited` (the run policy carries `_inherited`, set by the resolver), `override(repo)` (memoised: reads `repos.override_path` from `snapshot(repo)` at `snap.commit`, runs `check_base_shape`, the class errors and `validate_policy(kind="override")`, converts a legacy file) and `pol(repo)` (memoised under `("pol", full_name)`: `apply_override` then `clamp_guarded`). New check `policy` (`check_policy`, registered last in `CHECKS`, documented in the checks table of `docs/guides/admin.md`): override problems (`error`), loosenings (`warn`, subject `loosen:<key>`), a legacy file (`fix`, subject `override:convert`, a `files` action that replaces the file with the minimal override), a `workflow_params` template that is not in the effective list (`warn`), and, from p7, the detected proposals (`fix`, subject `override:propose`).

**Absent is not empty** (architect findings 1 and 3). In inherited mode:
- `rulesets.default_branch.required_status_checks` absent: `ruleset_bodies(cfg, live_checks=None)` takes the live ruleset's status-check contexts and keeps them; only an explicit `[]` removes the rule. A missing `tld-main` is created without a check rule. Without `extends` the behaviour is exactly today's.
- The release template entry with neither `workflow_params.release` nor its own `params` is not installed or rewritten: an `info` finding (subject `workflow:<dest>:standdown`) says so; the `policy` check proposes the parameters.
- No `release` section in the repository's resolved profile: the release template stands down with the same `info` finding (no value to compare).

A repository's override path gets one finding at most: when a legacy file also needs detected values, the converted override is merged with them (subject `override:convert`), so `apply_files` never sees two puts of one path. `apply_files(client, repo, changes, default_branch, commit, tree, today, notes=())` appends the notes under `Detected values (the owner confirms them):` as escaped bullets; `Action` gains `note: str = ""`; `apply_findings` passes the notes of a repository's file actions. Nothing else on the apply path changes.

### 3.8 Derived logins

`derive_logins(profile) -> (agent, reviewer, reasons)`: agent is `git.bot_login`; reviewer is `git.owner_login`, else the one `git.codeowners` entry when there is exactly one, it is a plain login (matches `^[A-Za-z0-9](?:[A-Za-z0-9-]*[A-Za-z0-9])?$`, no `/`, not the bot). An explicit `agent.agent_login` or `release.reviewer_login` in the effective policy wins and the profile is not read. The profile is the repository's resolved profile at its default branch, read by `repo_admin_profile.repo_profile` (added in p7 from the steps `check_profile` already runs, 3.12). The schema loses `required` for `agent_login` and `reviewer_login`; for a run policy without `extends`, `validate_policy` still reports the old `missing required key` text, so old files behave the same. With no profile or no value: a `warn` finding `<repo>: agent.agent_login is not set and cannot be derived (<reason>)` with the manual `set git.bot_login in the repository's profile or agent.agent_login in its override`, the role part skipped, the environment and secret part still run; for the release check `release.reviewer_login` likewise and the whole release check skipped for that repository (comparing reviewers with none would loosen it). The reviewer id lookup moves inside `one(repo)` (it is memoised per login).

The profile's `release.workflow` default (`tld-release.yml`) is already plan 90 section 3.1; this plan only reads it.

### 3.9 Detection (proposal only)

`repo_admin_detect.py`. Pure: `status_checks`, `release_params`, `tag_workflow_creates_release`, `own_release_workflow`, `detected_override`, `pr_notes`. I/O: `gather(ctx, repo)`.
- **Checks.** Samples are the newest `DETECT_PRS = 10` merged pull requests of the default branch (`GET /repos/{fn}/pulls?state=closed&base=<branch>&sort=updated&direction=desc&per_page=50`, keep those with `merged_at`). Per sample: `GET /repos/{fn}/commits/{head}/check-runs?filter=all&per_page=100` and `GET /repos/{fn}/commits/{head}/status`. `status_checks(samples)` returns `(names, excluded)`: fewer than `DETECT_MIN_PRS = 3` samples gives no names and the reason `too few merged pull requests (<n>)`; a name is kept only when it concluded `success` on every sample. Excluded, first matching reason: `flaky: success and failure on the same commit in #<n>`; `failed on #<n>`; `skipped on #<n>` (also `neutral`, `cancelled`, `stale`); `pending on #<n>`; `seen on <k> of <n> pull requests (path filter or new)`. Failure and flakiness do not depend on whether the API returns re-runs: a check that failed on any sampled head is excluded, because a merged pull request with a red check means the check is not reliable or was bypassed.
- **Release parameters.** `release_params(tags, manifests, tag_workflow)` returns `(params, notes)`: `tag_prefix` is the most common prefix of version-like tags (`^(\D*?)(\d+\.\d+\.\d+)(.*)$`; a tie goes to the prefix that sorts first; no such tag gives no params and the note `no version-like tags`); `version_style` is `semver` when a suffix matches `^-[0-9A-Za-z.-]+$`, `pep440` when a suffix matches `^(a|b|rc)\d+$`, else `pep440` when `pyproject.toml` is in `manifests`, else `semver`; `create_release` is `"false"` when `tag_workflow` is true; `check_script` is never guessed. `tag_workflow_creates_release(texts)` is true when a workflow text matches `(?ms)^\s*push:\s*\n(?:[ \t]+.*\n)*?[ \t]+tags:` and contains `gh release create`, `action-gh-release` or `create-release`. Tags: `GET /repos/{fn}/tags?per_page=100`; manifests: the top-level blobs `pyproject.toml`, `package.json`, `Cargo.toml`, `go.mod` of the snapshot; workflows: `ctx.automation_files`.
- **Own release workflow.** `own_release_workflow(profile_release_workflow, workflows)` returns the effective `workflows` list without the release template when the resolved profile names a release workflow other than `tld-release.yml` and the list has the release template, else `None`; with it, release parameters are not proposed.
- `detected_override(checks, params, workflows)` builds the override mapping; `propose_override(existing, detected)` keeps every key the repository already wrote; `render_override(doc)` writes a two-line comment header and `yaml.safe_dump(sort_keys=False)`. Names reach YAML only through `safe_dump` and the pull request body only through the existing `_cell` escaping.
- `gather` maps a check run whose status is not `completed` to no conclusion, else its `conclusion`; a commit status `success` to `success`, `failure` or `error` to `failure`, `pending` to no conclusion; its name is the check name or the status context.
- Detection repeats on every audit until the owner merges the proposal (a repository with fewer than three merged pull requests repeats it indefinitely); `audit` and `apply` accept `--no-detect` to skip it.
- Detection runs only for a repository whose effective policy has `rulesets.default_branch` and no `required_status_checks`, or the release template without parameters, or that has no override file; a failed call is an `unavailable` finding.

### 3.10 Reproduction and the delta

Fixtures in `tests/fixtures/admin-policy/` (placeholder organisations acme-a and acme-b): `shared-base.yaml` (the content of 3.11), `org-a.yaml` and `org-b.yaml` (run files with `org` and `extends` placeholders), `override-a.yaml` and `override-b.yaml`, and `legacy-a.yaml` and `legacy-b.yaml` (copies of today's two files; `a` is this repository's, `b` the second, with every value written out in the p8 brief). ## 5. Risks and open questions

1. **PR 104 moves.** It is open with owner decisions and fix rounds pending, so its head can change after this revision. A worker finds a name of 3.12 gone or renamed. Symptom: `ImportError` or `AttributeError` in p3, p4 or p7, or a failing PR 104 test after a merge of its new head. Stop with `status=blocked` and name what is missing; do not copy plan 90's code. mb1 brings the newest head in before the start.
2. **Reviews read PR 104 too.** Until PR 104 merges, implement's final review and the roles it runs compare with `origin/main` and so also read PR 104's 163 files; a finding in PR 104's code is not this plan's to fix. The `final_checks` item about those paths is how the reviewer is told; if the owner prefers a review of this plan's changes alone, merge PR 104 before implement starts. Never merge it while phases run (3.12). The three pinned admin test files are compared with `168bfa2` (this branch's merge of PR 104's head), so a newer head that changes them is reported, not edited.
3. **`compare` semantics.** The reachability check assumes `compare/<default>...<sha>` answers `behind` or `identical` for an ancestor. If the first real run refuses a valid pin, the status word differs: stop and report the answer.
4. **A ruleset that loses its checks.** Symptom: a `rulesets` fix whose body has no `required_status_checks` for a repository whose live rule has them. The keep-live rule of 3.7 is missing or reads the wrong ruleset.
5. **A tuned release workflow rewritten.** Symptom: `workflow .github/workflows/tld-release.yml differs from its template` for a repository without `workflow_params.release`. The stand-down of 3.7 is missing.
6. **Import cycle** `partially initialized module` between `repo_admin`, `repo_admin_profile`, `repo_admin_extends` and the two pure modules: the pure modules import nothing from `repo_admin`; `repo_admin_extends` imports `ApiError` and `validate_policy` inside functions; `repo_admin` already imports `check_profile` and `check_git_ops` at the top, and those modules reach `repo_admin` lazily through `_ra()`; `repo_profile` is called the same way.
7. **API budget.** Detection is about 22 calls per repository; a 429 in a large organisation means the first audit runs with `--repo` batches; the client already waits out one rate limit.
8. **Mutants.** `tests/core/test_mutants_file.py` fails when a mutant's `old` text no longer occurs once. p3 touches `src/tld/profile/base.py`, which PR 104's mutants cover (and whose 600-line bound `tests/adapters/claude/test_hooks_config.py` checks); p9 adds the new ones.
9. **The reproduction test cannot be made equal** without a difference beyond the listed delta: the key classes are wrong; stop and report the difference.
10. **No project words** (`tests/core/test_no_project_words.py`): organisation and repository names live in `tests/` and `docs/`, never in `src/`, `playbooks/` or `adapters/`; the word `pytest` stays out of `src/`.
11. **Open questions answered by default.** Item 13 of the architect's report: a repository with no `release` section in its profile has its release template stand down with an `info` finding. The shared base sets `admin_bypass: true` for every repository of both organisations, as the ask says. `config_dirs.require` is overridable (the ask is silent). Change 3.3 before implementing if you disagree.
12. **Stub eval.** The new eval task proves the fixture, grader and stub wiring, not the playbook's stop; the stop's precondition (`validate-policy` prints a line ending `repository override)`) is proved by a unit test, and a real run is the only proof of the stop itself.
13. **The tld-release environment everywhere.** The base gives every repository a `release` section, so the audit checks the `tld-release` environment and its secret in repositories that never release; the release workflow itself stands down when the profile has no release section. A repository that must not have the environment is excluded with `repos.exclude`.
14. **Flaky detection.** The rule does not rely on `filter=all` returning re-runs; it also excludes any check that failed on a merged pull request's head. No research request was needed.
