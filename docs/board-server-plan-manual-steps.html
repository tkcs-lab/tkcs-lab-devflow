Board Server Setup

Three things only you can do, all after the last phase has merged. The server, its client, its MCP bridge and the page are built and tested by the plan; hosting it and trying it with real sessions is yours.

Before implementation

Nothing. Every phase builds and tests against a local server, so you can start /implement right away.

After implementation

Host the board server behind HTTPS

about 30 min

The pull request does not run a server for you. Until you host one the board is empty and unreachable. Any machine that stays on and has Docker works. The full text of these steps is in docs/board-server.md once the pull request is merged; the design is in the plan, section 3.

Done when the three commands answer as expected. Report back one line: ma1: pass or what you saw.

Give the cloud environment the board URL, the token and network access

about 10 min

Sessions write to the board only when DEVFLOW_BOARD_URL and DEVFLOW_BOARD_TOKEN are set in their environment and the cloud environment's network policy lets them reach your host.

Done when a new session answers echo "$DEVFLOW_BOARD_URL" with your address. Report back: ma2: pass.

Check the board with a real session and a real scheduled task

about 25 min

Tests cannot show that the plugin's MCP bridge loads inside a cloud session, or inside an unattended one. This is the check that does. If the tools are missing, the sessions fall back to board_client.py, which still works; you only need to know which path you have.

Done when every step above matches. Report back, in the pull request, one line per step: ma3: tools in session yes/no · tools in scheduled task yes/no · scheduled health ok yes/no · page updated yes/no.

If the scheduled task has neither the tools nor a working health, say so in the pull request: the unattended commands then cannot write to the board until the environment of scheduled tasks is given the same two variables.
