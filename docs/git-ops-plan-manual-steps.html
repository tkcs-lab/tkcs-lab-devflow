Git Ops Setup

Everything here needs your hands: a repository, a token, an environment and a first real run. The code phases build against a stub, so none of it blocks /implement.

0 of 0 steps

Before implementation

Nothing to do. Start /implement whenever you are ready.

After implementation

1

Create the central repository

about 10 min

The workflow and its allowlist live in one private repository of their own, so the token is released only there. This page calls it tkcs-lab/git-ops; use another name if you like and replace it everywhere.

  1. Open New repository in tkcs-lab. Name it git-ops, set visibility to Private, tick Add a README file, and create it.

    You should see: an empty repository with a README on main.

  2. Open New branch ruleset. Name it protect-main, set Enforcement to Active, add the target Include default branch, and tick Restrict deletions, Block force pushes and Require a pull request before merging. Create the ruleset.

    You should see: protect-main listed as Active under Rulesets.

  3. Open Actions settings and set Workflow permissions to Read repository contents and packages permissions. Save.

    You should see: the read-only option selected.

  4. Optional, only if you use the second GitHub user: in the same ruleset also tick Require review from Code Owners, and add .github/CODEOWNERS containing * @your-login through a pull request. Setup of that user: second GitHub user. Without it, the rule that Claude never merges or approves its own pull request is the only guard on the workflow file.

    You should see: either the extra rule or a decision to skip it.

Done when tkcs-lab/git-ops exists, is private, and main cannot be deleted, force-pushed or pushed to directly.

2

Create the token and the environment

about 15 min

The token is the only credential that can touch other repositories. Storing it as an environment secret limited to main means an edited copy of the workflow on any other branch never receives it.

  1. Open New fine-grained token. Token name git-ops. Resource owner tkcs-lab. Expiration 90 days (add a calendar reminder to renew it).

    Repository access: Only select repositories, then pick every repository the workflow may touch. Start with claude-toolkit. The allowlist in step 3 must name the same repositories.

    Repository permissions: Contents: Read and write and Pull requests: Read-only. Leave everything else at No access. Generate the token.

    You should see: a string starting with github_pat_, shown once. Copy it. Never paste it into a chat.

  2. If the organisation requires approval for tokens, an owner approves it at Token requests. Skip this when it was approved automatically.

    You should see: the token marked Active in your token list.

  3. Open New environment in git-ops. Name it exactly git-ops and configure it.

    Under Deployment branches and tags choose Selected branches and tags, add the rule main. Leave Required reviewers off, otherwise every run waits for your click.

    You should see: the environment git-ops with one deployment branch rule, main.

  4. On the same environment page, under Environment secrets, choose Add environment secret. Name GIT_OPS_TOKEN. Value: the token from the first step. Save.

    You should see: GIT_OPS_TOKEN in the list with its value hidden.

Done when the secret exists on the environment, not on the repository and not on the organisation.

3

Install the workflow and the allowlist

about 10 min

GitHub only offers Run workflow for files on the default branch, so both files go into git-ops through a pull request.

  1. Open the workflow template and copy its content (Raw). Once the toolkit pull request is merged, replace feature/git-ops in that address with main.

    You should see: a file named devflow-git-ops.yml with no placeholders to fill in.

  2. In git-ops, choose Add file, Create new file. Path .github/workflows/devflow-git-ops.yml, paste the content, and commit to a new branch chore/add-git-ops.

    You should see: GitHub offering to open a pull request.

  3. On that branch add a second file git-ops-allowlist.json at the repository root, copied from the allowlist template. Set owner to tkcs-lab and list in repos the names of the repositories your token covers (a * glob is allowed). Keep the protected branch names the template lists.

    You should see: a JSON file whose repos list matches the token's repositories.

  4. Open the pull request and merge it.

    You should see: devflow-git-ops listed on the Actions tab.

Done when the Actions tab lists the workflow and main holds both files.

4

Run it once for real

about 10 min

Only a real run shows that the token works, that a branch name with a slash is handled and that a session can start the workflow. You will use a throwaway tag and a throwaway branch in claude-toolkit.

  1. Start a new Claude Code session on claude.ai/code with tkcs-lab/git-ops and tkcs-lab/claude-toolkit both selected. If the Claude GitHub App is missing on git-ops, install it from the installation page.

    You should see: both repositories in the session.

  2. Send this message. It names the tool and the inputs because the skill is not installed until the toolkit pull request is merged and the plugin updated.

    With the GitHub tool actions_run_trigger, run workflow devflow-git-ops.yml on ref main in tkcs-lab/git-ops with inputs repo=tkcs-lab/claude-toolkit, action=create-tag, name=v0.0.0-gitopstest.1, dry_run=true. Then read the run and show me its summary.

    You should see: a run titled git-ops create-tag v0.0.0-gitopstest.1 in tkcs-lab/claude-toolkit (dry run) that succeeds, with the summary Dry run: would create annotated tag v0.0.0-gitopstest.1.

  3. Send the same message with dry_run=false.

    You should see: the summary Created annotated tag v0.0.0-gitopstest.1, and the tag on the tags page.

  4. Ask Claude to create the branch chore/git-ops-test from main in claude-toolkit, then to delete it with the same workflow: action=delete-branch, name=chore/git-ops-test, first with dry_run=true, then with dry_run=false. The slash in the name is intended.

    You should see: Deleted branch chore/git-ops-test followed by a Restore: line, and the branch gone from the branches page.

  5. Ask for a dry run with action=delete-branch and name=main.

    You should see: the run fails with main is the default branch. Nothing is deleted.

  6. Delete the test tag from your own computer, because the workflow never deletes tags. The name matches the allowlist's tag_pattern, which is why it looks like a version:

    git push https://github.com/tkcs-lab/claude-toolkit :refs/tags/v0.0.0-gitopstest.1

    You should see: [deleted] v0.0.0-gitopstest.1 and an empty tags page.

Report back one line each for steps 2 to 5: passed, or what happened instead. If step 2 fails with a permission error on the dispatch, say so: the session cannot start workflows and you will start them from the Actions tab instead (the documentation explains how).
