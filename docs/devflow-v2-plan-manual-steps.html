Part 1 · Before implementation

1. Confirm the second GitHub user is in place

about 1 min
mb1-identity-done

You did this in the earlier experiments. The plan only asks you to confirm it, because the later phases assume it.

  1. The claude.ai connection at claude.ai/connect-github shows the second (agent) GitHub login, not yours.

  2. Every repository that runs /implement has a ruleset on its main branch (pull request, Code Owner review, one approval, dismiss stale approvals, approval of the most recent reviewable push, no force pushes) and a .github/CODEOWNERS with * @<your-login>.

  3. A throwaway pull request opened from a session showed the agent as author and "Review required".

Done when all three are true. If any is not, stop and tell me; the plan does not redo them.

2. Create the private scratch repository

about 20 min
mb2-scratch-repo

The spike phase (p7) tests Dependabot access, CI triggers and approval behaviour here, so nothing touches a real project. Use exactly this name: andras-tkcs/devflow-scratch. The order matters: seed the files first, add the ruleset last.

  1. Create the repository at github.com/new as andras-tkcs / devflow-scratch, Private, with a README so the main branch exists.

  2. Add these four files to main with GitHub's "Add file → Create new file" (commit straight to main; the ruleset does not exist yet).

    requirements.txt
    PyYAML==5.3
    .github/dependabot.yml
    version: 2
updates:
  - package-ecosystem: pip
    directory: "/"
    schedule:
      interval: daily
    .github/workflows/ci.yml
    name: ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - run: echo ok
    .github/CODEOWNERS
    * @andras-tkcs

    The old PyYAML pin is on purpose: it raises a Dependabot alert and a Dependabot pull request.

  3. Turn on Dependabot alerts, Dependabot security updates and Dependabot version updates at Settings → Advanced Security.

  4. Invite the agent user with Write (not Admin, not Maintain) at Settings → Collaborators, and accept the invitation while signed in as the agent user.

  5. Make sure the Claude GitHub App covers this repository: github.com/apps/claude/installations/select_target, then add devflow-scratch to the repositories it can see.

  6. Add the same ruleset you use on your real repositories to main at Settings → Rules → New branch ruleset: require a pull request; require review from Code Owners; 1 approval; dismiss stale approvals on new commits; require approval of the most recent reviewable push; require status check ci; require branches to be up to date; block force pushes and deletions. No bypass list entries for the agent user.

Done when the repository's Security tab lists at least one Dependabot alert for PyYAML, a Dependabot pull request (branch dependabot/pip/…) is open (it can take a few minutes), and a session can open the repository (list_repos shows it).

3. Prepare one approved pull request that is behind main

about 15 min
mb3-approved-pr

Spike item (d) asks whether an update-branch by the agent removes your approval. It needs a pull request that you approved and that is out of date. You need both accounts: use a private browser window for the agent user.

  1. As the agent user, on the scratch repository, use the web editor to create a new file spike-d-a.txt (content a) on a new branch spike/d-a and open a pull request titled spike d: approval test.

  2. As you, open that pull request and approve it (Review changes → Approve). Do not merge it.

  3. As the agent user, create spike-d-move.txt on a new branch spike/d-move and open a second pull request. As you, approve it and merge it once the ci check is green. This moves main ahead.

Done when the first pull request ("spike d: approval test") is open, shows "Changes approved" and says the branch is out of date with main.

Leave both Dependabot and the first pull request alone. Do not click "Update branch" yourself.

Part 2 · After implementation

4. Publish the board and point sessions at it

about 5 min
ma1-board-live

Verifies what no test can: the board on your phone and the push notification.

  1. In a new session on any repository that has the devflow plugin, run /board. It prints the board's address.

  2. In the claude.ai environment that your sessions and scheduled tasks use (the cloud environment menu in the session's title bar, then Edit), add the environment variable DEVFLOW_BOARD_URL with that address. It is not a secret. Only sessions started afterwards see it.

  3. Open the address on your phone. It should say "Nothing needs you" or list your running projects, in light and dark mode, with no sideways scrolling.

  4. Run /board prune. It lists records older than 7 days and asks before deleting any.

Report back: "Board opens on the phone: pass/fail. Push notification arrived: pass/fail."

6. Create the weekly scheduled tasks

about 10 min
ma3-scheduled-tasks

Each repository needs a profile section first: deps: for /deps, upstream: for /upstream (see docs/profile-reference.md after the merge). Today the two forks are PrivacyFence/peek and PrivacyFence/grist-core; a future fork gets its own profile and its own task the same way.

  1. For each repository you want kept current, add the deps: section to its .claude/toolkit.yaml (cooldown days, time budget in minutes, lockfile commands if any) and merge that change.

  2. For each of the two forks, add the upstream: section (upstream repository, tag pattern, version file), create the version file with the tag the fork is currently based on, and merge that change.

  3. In claude.ai/code, ask a session on the repository: "create a weekly scheduled task that runs /deps on Monday morning, in permission mode auto, in the environment that has DEVFLOW_BOARD_URL". Do the same with /upstream for each fork. (You can also create them in the Claude Code web app's scheduled tasks screen.)

  4. Fire each new task once by hand and check that a record appears on the board.

Report back: "deps task fired and wrote a board record: pass/fail. upstream task fired and wrote a board record: pass/fail."

7. Set up repositories that use /land

about 15 min per repository
ma4-land-repos

/land installs a workflow that updates the next auto-merge pull request after each merge. The workflow needs the agent's token as a secret, and the repository must allow auto-merge. Do this for each repository that will use /land.

  1. In the repository's Settings → General → Pull Requests, tick Allow auto-merge (address: https://github.com/<owner>/<repo>/settings).

  2. Signed in as the agent user, create a fine-grained token at github.com/settings/personal-access-tokens/new: only the repositories that use /land, repository permissions Contents: Read and write and Pull requests: Read and write, expiry 90 days. Copy it once.

  3. In each repository, open Settings → Secrets and variables → Actions (https://github.com/<owner>/<repo>/settings/secrets/actions) and add a repository secret named exactly DEVFLOW_AGENT_TOKEN. Paste the token only into that GitHub form, never into a chat or a file.

  4. Run /land in the repository. Review and merge the pull request that installs the workflow (.github/workflows/devflow-land.yml) first.

  5. With two agent pull requests open, run /land again, approve both, and press "Enable auto-merge" on each. After the first merges, the second should be updated by the workflow, run CI again and merge without you touching it.

Report back: "Second PR updated automatically after the first merged: pass/fail. Your approval stayed on it: pass/fail."
